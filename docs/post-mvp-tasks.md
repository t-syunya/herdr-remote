# MVP 後の機能拡張タスク

作成日: 2026-09-23。各タスクは未着手。

## 方針

MVP（Phase 0〜6）は完了し、現在の動作は利用上問題ない。今後は機能拡張を中心に進める。
PC は基本的に常時起動するため、常用向け配信、自動起動、運用手順の整備は当面の対象外とする。
現在の起動方法を継続し、運用面で具体的な不便が生じた場合に再検討する。

完成版の中核は「見やすく操作できる」「複数 Agent を管理できる」
「作業場所をスマホから作成・整理できる」の3点とする。まず優先順1〜3を進め、
4〜5は追加の利便性向上、6は必要性に応じた拡張として扱う。

Herdr 固有の API は引き続き `packages/herdr` に閉じ込める。接続先は Tailscale 内に限定する。
本書はタスク計画であり、公開 API の変更、新規の本番依存関係、外部サービスへの書き込み等は、
実装時にリポジトリの確認ルールに従う。

## 1. 出力閲覧・入力の改善

対象: 主に `apps/web`。

- [x] 出力の末尾を見ている場合は更新に追従し、過去の出力を読んでいる場合はスクロール位置を維持する。
- [x] 最新位置へ戻るボタンと出力のコピー操作を追加する。
- [x] 入力欄付近に送信先を表示し、ペインへのテキスト送信と Agent へのプロンプト送信の挙動を明示する。
- [x] ペインへの送信はテキストの後に Enter を自動送信する。必要な場合は Enter を送らず本文だけ送る、または本文送信後に Enter を手動送信できる操作を用意する。Agent prompt 送信には混同して適用しない。
- [ ] iPhone の日本語入力、複数行入力、ソフトウェアキーボード表示時のレイアウトを調整する。
- [ ] 画面復帰・通信復旧時に一覧と出力を再取得し、消失した対象の選択を解除する。
- [ ] Herdr のタブ切替時に切替先のペイン・Agent一覧を再取得し、有効な選択対象があれば出力も更新する。旧タブの選択や出力を残さない。
- [ ] 最後に選択したワークスペース・タブをブラウザー内に保存し、次回起動時に一覧を再取得してから復元する。保存先が存在しない場合は有効な選択先へ戻す。
- [ ] 出力が行数または応答サイズの上限に達しても読み取りを失敗させず、古い行から省いて最新部分を表示する。単一の長い行が上限を超える場合も末尾側を残し、省略状態を明示する。
- [ ] 通信のタイムアウト、最終更新時刻、古い出力を表示中であることを扱う。
- [ ] 送達不明の入力は自動再送せず、利用者が出力を確認して判断できる表示にする。

完了条件: 実機 iPhone で、出力を読み返しながら入力できる。画面復帰や通信断後も
再読み込み操作に頼らず表示を更新できる。タブを切り替えたときに一覧と選択中対象が自動更新され、
再度開いたときは前回のワークスペース・タブに戻る。大きな出力でも最新部分を読めて、
省略された場合はそれが分かる。ペイン送信では既定で Enter が送られ、必要なら送信方法を選べる。
古い情報や送達不明を成功と誤認しない。

## 2. 複数 Agent の管理改善

対象: 主に `apps/web`。必要な情報が不足する場合は安定したアダプター契約から検討する。

- [ ] Agent の所属ワークスペース・タブを表示し、同種・同名の Agent を区別しやすくする。
- [ ] 状態による絞り込みを追加する。
- [ ] 対応待ち・完了の Agent を見つけやすくする。
- [ ] リモート画面での選択と Herdr の focus 操作を連動させるか決める。
- [ ] `done` の既読扱いを決め、必要な Herdr の挙動を実機確認して実装する。

完了条件: 複数ワークスペースの Agent から、対応が必要な対象とその所属を判別して選択できる。
単なる出力閲覧と既読化の関係が明確で、`unknown` を完了として扱わない。

## 3. ワークスペース・タブ・ペインの操作

対象: `packages/herdr` → `apps/server` → `apps/web`。

- [ ] 作成・名称変更・分割・終了について、対象ごとの対応可否、入力、返却値、失敗時の挙動を実機で調査する。
- [ ] 調査結果を `herdr-api-spike.md` に追記し、利用可能な操作と制約を整理する。
- [ ] ワークスペース・タブの作成と名称変更を、実機で確認した対応範囲で追加する。
- [ ] ペインの作成・分割を追加する。
- [ ] 終了操作に、対象と影響範囲を示す確認を設ける。
- [ ] 作成・変更・終了後の一覧更新と選択先を整える。操作対象が先に消失した場合も扱う。

完了条件: iPhone から作業場所を作成・整理できる。誤った対象を終了しにくく、
操作失敗後も一覧と選択状態の整合性が保たれる。未対応操作を想定だけで実装しない。

## 4. 入力の省力化

対象: 主に `apps/web`。保存範囲は着手時に決める。

- [ ] よく使うキー操作のカスタムショートカットを追加する。
- [ ] プロンプトテンプレートを選択して入力欄へ挿入・編集できるようにする。
- [ ] 対象切り替え時に下書きを保持し、別の対象の入力と混ざらないようにする。
- [ ] 下書き・テンプレート・設定を、画面内だけで保持するか端末に保存するか決める。
- [ ] 対象消失や Herdr 再起動時の下書きの扱いを決める。Pane ID を永続的な Agent の識別子とみなさない。

完了条件: 繰り返し入力を減らせる。テンプレートの挿入だけでは送信されず、
対象切り替えによって下書きが失われたり別の対象へ誤送信されたりしない。
永続化を採用する場合は、保存内容と削除方法を明確にする。

## 5. ホーム画面からの利用

対象: `apps/web` と必要最小限の配信設定。

- [ ] 実機 iPhone でホーム画面追加・単独画面表示に必要な配信条件を確認する。
- [ ] PWA 用のメタデータとアイコンを整備する。
- [ ] ホーム画面から起動した場合のレイアウトと画面復帰を確認する。
- [ ] 更新時に古い UI と API の組み合わせが残らないよう、キャッシュ方針を決める。
- [ ] 切断中であることを明示し、操作要求をオフラインで蓄積・後送しない。

完了条件: ホーム画面から開いて通常の操作ができ、更新後も利用を継続できる。
配信設定の変更が必要な場合は範囲を先に整理し、運用整備全般へ拡大しない。

## 6. 必要に応じたリアルタイム更新・通知

この項目は完成版の必須条件にしない。

- [ ] 現在のポーリングで、更新待ちや負荷が実際に問題になるか確認する。
- [ ] 問題がある場合に限り、ポーリング改善と SSE / WebSocket を比較する。
- [ ] イベント方式を採用する場合は、購読開始時・切断時・再接続時の挙動を実機で確認する。
- [ ] アプリを閉じている間の完了・対応待ち通知が必要か、利用状況から判断する。
- [ ] 通知を採用する場合は、配信方式、権限、通知内容、重複防止、追加基盤の必要性を別途設計する。

完了条件: 採用理由が具体的な利用上の問題と結びついている。イベントを取り逃した場合も
一覧・出力の再取得で復旧できる。通知基盤は明示的に採用を決めてから追加する。

## 各タスクの検証

- 関連する lint・format・typecheck・build を確認する。
- 入出力、対象の切り替え、異常系、アダプターと RPC の境界について、変更に必要な回帰テストを追加・実行する。
- UI の変更は実機 iPhone で確認し、画面幅だけの検証と区別する。
- 通信断、画面復帰、対象消失、送信中の切断について、変更の影響範囲を確認する。
- 完了時に実施した検証と未確認事項を記録する。
